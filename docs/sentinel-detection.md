# Threat Detection with Microsoft Sentinel

A Log Analytics workspace with Microsoft Sentinel onboarded on top, fed by monitoring built directly into the Terraform rebuild. This document covers the detection layer specifically; for the underlying infrastructure it monitors, see [`terraform-build.md`](./terraform-build.md).

## Data Pipelines

Three genuinely different Azure mechanisms feed this workspace — worth distinguishing precisely, since they're not interchangeable:

- **Native Sentinel data connector** (`azurerm_sentinel_data_connector_azure_security_center`) — pipes Microsoft Defender for Cloud's own generated alerts directly into the `SecurityAlert` table. This connector consumes Defender's finished analysis, not raw logs.
- **Subscription-level diagnostic setting** — Azure Activity Log (resource creation, deletion, role assignments) routed into the `AzureActivity` table, targeting the subscription itself as the resource (via a `data "azurerm_subscription"` lookup), not any single resource.
- **VNet Flow Logs with Traffic Analytics** — network flow data captured via Network Watcher, written to a dedicated storage account and enriched into the same Log Analytics workspace, on a 60-minute interval.

## Analytics Rules

Three KQL scheduled analytics rules were built, targeting three different tables — deliberately exercising three different pipelines rather than writing three rules against the same data source:

| Rule | Table | Status |
|---|---|---|
| NSG rule change detection | `AzureActivity` | ✅ Live, confirmed against real data |
| Defender for Cloud high-severity alerts | `SecurityAlert` | ✅ Live, confirmed against real data |
| SQL failed authentication | `AzureDiagnostics` | ⚠️ Deliberately undeployed — see Finding below |

The first two were confirmed not just by successful `terraform apply`, but by running their exact KQL directly against the live workspace and observing real matching rows — genuine activity generated by Terraform's own execution (role assignments, resource operations) and by Defender's own background scanning.

## Finding: SQL Auditing Did Not Reliably Reach Log Analytics

The third rule's query (`AzureDiagnostics | where Category == "SQLSecurityAuditEvents"`) consistently returned zero rows, including after deliberately generating a real failed SQL login. Root-caused through direct verification rather than assumption:

1. **Ruled out ingestion lag** — an unfiltered `AzureDiagnostics | take 10` also returned nothing, ruling out a simple timing delay.
2. **Ruled out the generic diagnostic-setting path** — a `azurerm_monitor_diagnostic_setting` targeting the SQL database, with `SQLSecurityAuditEvents` as the enabled log category, was confirmed present and correctly configured, but produced no data.
3. **Checked native SQL Auditing directly in the portal** — found that the server-level "Enable Azure SQL Auditing" toggle was on, but *no destination* (Storage, Log Analytics, or Event Hub) was actually checked. The `log_monitoring_enabled = true` argument on `azurerm_mssql_server_extended_auditing_policy` toggled auditing on, but did not reliably specify a Log Analytics destination — a genuine, documented inconsistency in how this specific Terraform resource maps to the underlying Azure feature (also reflected in multiple open issues against the `azurerm` provider).
4. **Confirmed authoritatively via the workspace's own Tables view** — `AzureDiagnostics` showed no assigned data plan and no retention value at all, unlike `AzureActivity`'s fully-provisioned entry, confirming the table had genuinely never received data rather than just appearing empty in a query.
5. **Manually enabled the Log Analytics destination directly in the portal** as a targeted test — confirmed this was the actual missing link, since native SQL Auditing's Log Analytics routing operates independently of the generic diagnostic-setting mechanism, mirroring exactly the SQL diagnostic settings conflict documented in Phase 1.

Given this is a genuine, confirmed platform-level gap rather than a configuration mistake, the rule was left deliberately undeployed (`count = 0` in Terraform) rather than shipped in a state that would silently never fire. This is consistent with Phase 1's own stated principle: automated telemetry should not be assumed correct without direct verification.

## Workbook

A custom Sentinel workbook, defined as Terraform-managed JSON (`azurerm_application_insights_workbook`, `jsonencode()`), containing three query panels matching the three analytics rules above. Unlike HCL, workbook JSON is not validated by `terraform plan` or `apply` — only genuine portal rendering confirms correctness. Verified live: the workbook renders correctly, including its title and all three panel headers; the two data-backed panels return real results, and the SQL panel correctly shows no results, consistent with the finding above.
